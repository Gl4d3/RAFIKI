Build Phase 1 of RAFIKI — an AI-powered personal finance companion for Kenya.
This is a monorepo application. The stack is React + TypeScript on the frontend,
Python + FastAPI on the backend, Supabase for the database, and Gemini as the LLM.

---

THE CORE ARCHITECTURAL PRINCIPLE

There are two distinct systems in this application and they must never be conflated:

THE ACCOUNTANT is pure Python code. It handles all financial math, ledger logic,
and rule enforcement. It is 100% deterministic. It never calls an LLM. It receives
structured data and returns structured data.

RAFIKI is the AI layer. It uses Gemini to interpret uploaded statements, ask
clarifying questions, and build a financial model of the user. In Phase 1,
RAFIKI only operates during the onboarding process — it analyzes statements
and conducts a gap-filling conversation. The ongoing chat interface is out of
scope for this phase.

---

WHAT THIS PHASE MUST ACCOMPLISH

The onboarding flow is the entire product for Phase 1. By the end of onboarding,
the system must have built a working financial model of the user — a structured
database representation of their obligations, patterns, counterparties, and
priority rules — derived entirely from their uploaded M-Pesa statement and a
short guided conversation with the AI.

The flow has five stages:

STAGE 1 — STATEMENT UPLOAD
The user uploads their M-Pesa statement (PDF or CSV format). The UI should
clearly communicate that this is how RAFIKI learns about them — not a form
they fill in, but a handover to a trusted system. The upload should support
both file formats. There should be a secondary optional field for a bank
statement. Include a privacy reassurance.

STAGE 2 — SILENT ANALYSIS
After upload, the system parses the statement in the background. Show a calm
loading state with narrative progress labels that update as processing moves
through stages: reading the file, identifying transactions, finding patterns,
preparing results. This should feel like the system is genuinely thinking, not
just waiting. Show a percentage progress indicator.

The backend processing during this stage must do real work:
- Parse all transactions from the statement (amount, counterparty, date, direction)
- Cross-reference counterparties against a hardcoded lookup table of known Kenyan
  paybill numbers and merchants (KPLC, Zuku, Safaricom postpaid, Nairobi Water,
  Naivas, Carrefour, Quickmart, Uber, Bolt) — these are auto-categorised
- Identify recurring transactions by finding the same counterparty appearing
  multiple times with similar amounts and regular timing
- Flag any counterparty that appears more than twice and cannot be auto-resolved
  as an "unknown" requiring user clarification
- Calculate category totals (transport, food, utilities, etc.)
- Identify the likely salary deposit (largest single credit, most regular timing)
- Store all results to the database

STAGE 3 — THE REVEAL
Before asking any questions, RAFIKI shows what it already knows. This should
present the top findings from the analysis conversationally — not as a form or
a dashboard, but as RAFIKI speaking. Lead with the most surprising insight first
(typically the transport total). Present each finding as a statement the user
can confirm or correct. Design this as a chat-style message from RAFIKI with
two response options at the bottom: confirm everything looks right, or flag that
something looks off.

The data shown here must come from real analysis of the uploaded file — not
hardcoded placeholder values.

STAGE 4 — GAP-FILLING CONVERSATION
For each unknown counterparty identified in Stage 2, RAFIKI asks one question
at a time in a conversational interface. Show progress (e.g. "3 of 5 unknowns
resolved"). Each question presents the raw transaction details and asks the user
to categorise the counterparty from a list of options relevant to Kenyan context:
Family or relative / Chama or savings group / Business expense /
Regular merchant / One-time payment / Something else.

When the user selects an option for a counterparty, that answer is written to the
database and the next unknown is shown. If the user selects "Something else",
allow a short free-text description. There must be a "Skip for now" option on
every question.

This stage is powered by Gemini — use the AI to generate natural, contextual
questions about each unknown rather than a generic template. Pass the transaction
details (amount, frequency, timing, any name hints from the counterparty string)
to Gemini and have it produce a specific, human question.

STAGE 5 — PRIORITY STACK REVIEW
After gap-filling, RAFIKI presents a suggested Priority Stack — the ordered list
of the user's financial obligations ranked by importance. This is generated by
the Accountant (deterministic Python logic) based on what was learned in Stages
2-4. The user can reorder items by dragging. Each item shows the obligation name
and the monthly amount identified from the statement analysis.

Below the stack, show a "Safe Buffer" field — the minimum balance the user wants
to always keep available. Pre-populate with a sensible default (KSh 2,000) but
let the user edit it.

A confirmation button saves the final priority stack to the database and marks
onboarding as complete. The user then lands on the Home screen.

---

THE HOME SCREEN

After onboarding, show the Home screen. This screen is informational in Phase 1
— it shows the results of what RAFIKI learned, but does not yet initiate any
financial actions.

Show:
- The user's display name or initials
- Their available balance (calculated by the Accountant from the financial model,
  not a live API call — use the data from the statement analysis)
- A financial health score (a simple integer 0-100 calculated by the Accountant
  based on savings rate, goal progress, buffer adequacy)
- A summary of the priority stack that was just built
- Quick-access cards for the three most common actions the user will want in
  future phases: "Send me money", "How am I doing", "What's coming up" —
  these can be non-functional stubs in Phase 1, they just need to exist visually

BACKEND EXPECTATIONS

Organise the backend into at least these conceptual areas:

An ingestion layer that handles file uploads, validates the format, and runs the
parsing pipeline. The parser must handle both M-Pesa PDF and CSV formats. For PDF
parsing, use pdfplumber. For CSV, standard Python csv library. The parser output
should be a normalised list of transaction objects regardless of input format.

A deterministic financial engine (the Accountant) that takes the parsed
transaction list and computes: spending totals by category, recurring obligation
detection, salary identification, and the initial priority stack suggestion.
This must be pure Python functions — no AI involved.

An AI analysis layer that uses Gemini to: generate the reveal message in
RAFIKI's voice from the Accountant's structured output, and generate contextual
gap-filling questions for each unknown counterparty.

A data layer using Supabase. The schema must capture: users and their onboarding
state, parsed transactions with their categories and tiers, resolved entities
(the knowledge graph of counterparties), extracted financial facts, the user's
priority stack, and a log of onboarding progress so the flow can be resumed if
interrupted.

REST API endpoints connecting frontend to backend. The onboarding flow needs:
an endpoint to receive and begin processing an uploaded statement (async, returns
a job ID), an endpoint to poll processing status and retrieve results when ready,
an endpoint to submit a user's answer to a gap-filling question, and an endpoint
to save the final confirmed priority stack.

FRONTEND EXPECTATIONS

Mobile-first React application. Maximum width 390px on mobile, centered on
desktop with no horizontal scroll. Use Inter as the typeface (import from Google
Fonts). The design language is minimal and calm — think editorial, not fintech.

Design tokens to apply throughout:
- Deep teal #00342B as the primary brand colour
- Warm indigo #4755B6 as the secondary/accent colour
- Off-white #F9F9F9 as the page background
- White #FFFFFF for card surfaces
- #1A1C1C for primary text (never pure black)
- #3F4945 for secondary and muted text
- 24px border radius on main cards
- No visible borders between sections — use background colour shifts instead
- No bold font weight anywhere — use medium (500) as the maximum weight
- All interactive elements minimum 48px touch target height

The five onboarding screens plus the home screen should be fully implemented
with real data binding — not hardcoded placeholder values. Every number shown
in the Reveal stage and the Priority Stack review must come from the actual
analysis of the uploaded file.

Navigation between onboarding stages should be smooth and directional.
If the user has partially completed onboarding and returns, resume from where
they left off using the onboarding state stored in the database.

SUCCESS CRITERIA FOR THIS PHASE

A user should be able to:
1. Upload a real M-Pesa statement (PDF or CSV)
2. Watch the system analyse it with meaningful progress feedback
3. See RAFIKI reveal what it found — with real numbers from their actual file
4. Answer questions about unknown transactions in a natural conversational flow
5. Review and confirm a priority stack that reflects their real financial life
6. Land on a home screen showing their financial model

The onboarding must work with a real M-Pesa statement file. Do not build it
around hardcoded data. The AI analysis must be genuine — Gemini should be
reading actual transaction data and producing contextual outputs.
